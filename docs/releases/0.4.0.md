# Joinery 0.4.0

Not released yet. Changes since [0.3.0](0.3.0.md).

## Added

- VR (ADR 0039). A **VR** feature for the 3D starting points turns on
  Godot's built-in OpenXR (nothing is downloaded) and carries an XR rig on
  the player: greybox hands, a pointer ray, grab and throw, smooth move,
  snap turn (30° or 45°), teleport with an arc that only lands on floor, a
  comfort vignette, seated play and a left-handed swap, all on a **VR
  comfort** settings page; the menus show on a panel in front of you.
  Without a headset the game starts on the desktop and says so. A new **VR
  room** starting point: a greybox room to walk and teleport in, with things
  to pick up, a button and a goal, its brief and a `vr-3d` bible preset
  (comfort, true scale, 72/90 fps and polygon budgets). VR is refused for 2D
  starting points with the reason. Real headsets were not available for
  testing; the rig was tested in a simulated mode (see the ADR).

- Playtests (ADR 0038). `/playtest` starts the playtester: your provider in
  the read-only `playtester` role (ADR 0037) plays the game headless with a
  seeded bot and writes a short report of bugs with repro steps and the
  seed, softlocks and balance notes, each with a severity. Its card shows
  **Playing… 0:42 / 2:00**, then counts
  by severity and each finding with its place in the code, seed and a
  screenshot; **Fix this** and the playtester's **Ask Journeyman to fix**
  lines put a ready request in the message box.
  - The bot plays every blueprint through its own input map (walking,
    jumping, interacting, heading for coins, pickups, checkpoints and goals,
    clicking the card game's buttons), pauses and resumes, saves and loads
    where the game can, and checks menu text in every language and the
    pseudo-locale. Custom games get the same error capture with plain random
    input.
  - It reports script errors and warnings with their script line, crashes,
    freezes, softlocks, falls out of the world, physics blow-ups, frame
    hitches, memory and node counts that only grow, text that doesn't fit, and
    level timings and deaths as balance notes.
  - `joinery playtest --project <path> [--minutes N] [--seed S] [--scene
    res://…] [--json]` runs it from the command line; a seed replays a run
    exactly. Runs never write into the game: reports, pictures and the game's
    own saves stay in `.joinery/playtests/`.
  - Journeyman, its tasks and the playtester have a read-only
    `playtest(minutes?, seed?, focus?)` tool, the same for Codex, Claude
    Code, Gemini CLI and opencode.
  - `[agents] playtest_after_change = true` plays after each accepted change
    to scripts or scenes; `playtest_minutes` sets the run length.
- References and design documents when you set up a game. The wizard's last
  step takes reference pictures (dropped or added, each with what to take from
  it) and design documents (Markdown, text or PDF); Project apps (`/setup`)
  adds them to a game that already exists, as one change you can revert.
  Pictures land in `art/reference/`, recorded as your import and on the art
  bible's reference board; documents land in `design/docs/`, are listed in the
  game brief, and Markdown and text ones fill its open sections word for word
  from matching headings. Agents read the documents with the brief and see the
  pictures with the art direction. `joinery new` and `game apply` take
  `--reference PATH[=note]` and `--design-doc PATH`; `joinery references add`
  does the same for an existing game.
- Several agents at once (ADR 0036). While Journeyman works, **Run alongside**
  in the message box starts a message as its own task, and Journeyman can hand
  an independent part of a request to a parallel task itself (`start_task`,
  with `task_status`, for Codex, Claude Code, Gemini CLI and opencode alike).
  Each task runs in its own session with the chat's provider and model, makes
  its own staged change and is reviewed on its own in the Review tab, with
  the same before/after panel, renders, Details, Accept and Discard as
  Journeyman's own change (one panel at a time; a task's never opens over
  Journeyman's).
  - Each task has a card above the message box with its title, apps, step
    (starting with "Starting <provider>…"), timer and its own Stop; the sidebar says "3 agents working" while two or
    more work, and Stop on Journeyman's request offers to stop the tasks too.
  - Two agents never change the same file: a task that tries is told which
    task has it ("… is being changed by another task: Make a desk lamp. Work
    on something else or wait."). A staged change follows changes accepted
    meanwhile, `joinery.lock` entries are merged, and a file changed on both
    sides is redone by the task, never merged silently. Each accepted change
    is still one Timeline commit. Claims are kept up to date from what each
    call wrote, not by re-reading the whole project after every call.
  - Game features change one at a time: a task adding or removing one, or
    `/feature`, holds them and anyone else is told who does. The game
    manifest is merged feature by feature on accept.
  - One agent at a time changes the scene on screen live: Journeyman's own
    request while it works, and a task once it is idle. Others change scenes
    that aren't open, as files. Tasks can't start tasks.
  - Blender and Krita document operations from different tasks take turns.
  - Every task runs the same policy hook; a Rule Zero stop in any of them
    stops every agent of the chat.
  - `[agents] parallel` in `joinery.toml` sets how many agents may work at
    once, Journeyman included (default 3, at most 6; `1` turns tasks off).
  - Saved chats record each task's start and outcome, and a chat continued
    from a summary mentions them.
- A review you take in at a glance (ADR 0040). One before/after view sized to
  the panel: textures, selected parts and live scene edits as one picture split
  by a line you drag, models from two angles, sounds as A/B with their
  waveform, code as only the changed lines, and a filmstrip when a change has
  several items. Under it one line of facts ("Door 20% wider · wood darker ·
  2 files", with up to three `facts` from `submit_for_review`), "Checks
  passed", and a reviewer's notes as one line. Discard and Accept are always on
  screen; **Details** holds files, diffs, checks and notes. Enter accepts,
  Backspace or Delete discards, A or B flips before and after.
  - A small change is decided from its chat card: a tiny picture, the facts
    line and Discard / Accept. A bigger one offers Review.
- Reviewer and debugger agents (ADR 0037). Every agent now has a role (lead,
  worker, reviewer, debugger) judged by the shared policy hook and gateway, the
  same for Codex, Claude Code, Gemini CLI and opencode; reviewers and debuggers
  only read and can never approve, accept, discard or edit the art bible.
  - A reviewer agent reads each change after Joinery's checks and before you
    see it ("Reviewing the change…"), against the request, the diff, the art
    bible, the game brief and the staged images. A real problem goes back to
    Journeyman to fix (at most twice); the review then shows its notes in the
    review's notes line, with every note in **Details**. It is skipped, and
    the review says so, after 90 seconds or on an error. Settings → Project
    → **Reviewer agent** and **Reviewer model** (`[agents] reviewer`,
    `reviewer_model`, `joinery reviewer`); `joinery transactions list` shows
    each change's `review_notes`.
  - `/debug`, or **Debug** on the offer after a new error in Godot's Output,
    starts a "Debugging: <error>" card: a debugger reads the error, Output and
    the game's log, can run the game headless offline to reproduce it, and
    finds the cause; a worker then makes the fix as a normal reviewed change.
- More you can do with a picked part of a model (ADR 0028, slice 2). A texture
  map can become its own source, a Krita painting (or a Material Maker graph)
  that starts from the map's pixels; painting adds fill, stroke and filter
  layers, and the model's map follows. A map can take any image a project tool
  made. "Make a copy for Head only" gives some objects their own copy of a
  shared material and its maps. Bones can be renamed, moved, re-parented and
  scaled as a chain; shape keys set, renamed, deleted or made from the current
  mix or pose. Each stays inside the picked part and replays with
  `joinery rebuild`; the part's chip tells Journeyman which operations fit.

## Changed

- The Godot tools run in the offline MCP worker (ADR 0041). The pinned Godot MCP
  is built into `joinery-mcp-worker` from its hash-checked commit and lockfile,
  and runs there with no network and the image's headless Godot, reading your
  project read-only; your machine no longer needs Node.js for it. Paths the
  agent sends and reads stay your project's paths. Run `joinery bootstrap` once
  to rebuild the worker; until then Godot says Rebuild (or Needs Docker when
  Docker is stopped) instead of running a server on your machine.
- MPFB2 humans export with their body shape baked in: the macro shape keys
  (`$md-…`, age, weight, proportions) no longer reach the game as morph
  targets (a default human's GLB drops from 8 to 0 and from 3.2 MB to 1.1 MB).
  Expressions and other shape keys stay. `keep_macro_shape_keys` keeps them,
  per model, and later edits remember the choice.

## Fixed

- Save and load: a save made after the level ended (from the pause menu on the
  result screen, or a throttled autosave that came due after the last hit) could
  load a defeated top-down player with no result panel and no way on. Once a
  level announces its end, Save is disabled with the reason ("The level is
  over. Play again to save.") and autosaves wait for the next level
  (`SaveGame.level_over`, `save_blocked_reason`; `save_slot` returns
  `ERR_UNAVAILABLE`). Saves older builds made in that state now load into the
  result screen again in the top-down, first-person and VR starting points.
  Save files are unchanged. `Menus.add_entry` takes an optional `reason` shown
  under a disabled entry. The playtester saves on the result screen again and
  reports a save that loads a level nobody can play.
- Parallel tasks take turns on every app a map operation runs. Painting a map,
  making it editable or putting an image in it, and the other typed Blender
  part operations, ran without holding any worker slot, so a Krita or Material
  Maker edit of another task could run at the same time. Each operation now
  holds Blender plus its Krita or Material Maker slot for the whole call; the
  other task's card says "Waiting for Krita" (or Blender, or Material Maker),
  and the slots are given back when the call fails or is stopped.
